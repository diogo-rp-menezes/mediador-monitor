# PostgreSQL local com Docker

O ambiente local usa Docker Compose e PostgreSQL 18.6. O serviço fica publicado somente em `127.0.0.1:54329`, tem healthcheck e mantém os dados no volume nomeado `mediador-monitor_mediador-postgres-data`.

## Inicialização

O projeto inclui um `.env.docker` ignorado pelo Git, com senha aleatória criada localmente. Se estiver preparando outra cópia, crie o arquivo a partir de [.env.docker.example](../.env.docker.example) e substitua a senha de exemplo por uma senha aleatória forte. Não compartilhe esse arquivo.

```powershell
npm run db:up
docker ps --filter "name=mediador-postgres"
```

Use `npm run db:logs` para acompanhar o banco e `npm run db:down` para pará-lo mantendo o volume. **Não use `docker compose down -v`** se quiser preservar os dados locais.

O endpoint Node de conexão está em [src/postgres.ts](../src/postgres.ts). A configuração vem das variáveis `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` e `PGSSLMODE`; `npm run build` compila esse módulo. A conexão foi verificada localmente com uma consulta PostgreSQL real.

### Pré-auditoria do banco SQLite legado

`npm run postgres:auditar-importacao -- --source data/mediador.db --report data/import-audit.json` gera um inventário somente leitura de tabelas e contagens SQLite/PostgreSQL, verifica vínculos tenant-scoped, arquivos originais e hashes, e impede indicar prontidão quando encontra órfãos, arquivos inconsistentes ou destino PostgreSQL já populado. Caminhos relativos de documentos são resolvidos primeiro a partir da raiz de execução do aplicativo e depois da pasta do banco. A auditoria usa `PGAPPUSER` e configura escopo global apenas dentro de uma transação de leitura para enxergar contagens protegidas por RLS. O JSON contém caminhos absolutos e identificadores de registros; mantenha-o local. Em 9 de outubro de 2026, os cinco arquivos que a auditoria marcava incorretamente como ausentes foram encontrados e seus hashes passaram; a importação continua bloqueada porque há três eventos de auditoria no PostgreSQL. Essa verificação não importa dados e “sem bloqueios conhecidos” não significa equivalência completa nem autoriza trocar o banco ativo. A importação retomável ainda exige mapear todas as tabelas e segredos, definir política para conflitos de IDs e testar reconciliação num clone isolado.

### Isolamento RLS em preparação

A migração `008_row_level_security.sql` habilita e força RLS nas tabelas com `escritorio_id`; sem `app.escritorio_id` na transação, políticas negam acesso. `withPostgresOfficeTransaction` define escritório e desativa acesso global com `SET LOCAL`; `withPostgresGlobalTransaction` é reservado a autenticação, seleção de contexto e administração global, também só durante a transação. `npm run postgres:validar-rls` simula dois escritórios com papel `NOLOGIN/NOBYPASSRLS`, verifica negação sem contexto e acesso global explícito, e reverte os dados e DDL de teste. A migração 008 está aplicada no Docker local. O servidor aceita `APP_POSTGRES_CONTEXT=1` para encaminhar autenticação, gestão de contexto, decisões, publicações e portal aos handlers PostgreSQL pelo pool `PGAPPUSER`; com `0` (padrão), mantém o comportamento SQLite. A rota `/` em modo PostgreSQL abre a tela de contexto e não o painel global legado. O dashboard, monitor, fluxos não portados e bootstrap PostgreSQL ainda não estão integrados, então este opt-in é para validar os fluxos PostgreSQL disponíveis, não uma troca completa do banco.

O papel runtime é separado do usuário administrativo `PGUSER`. Defina `PGAPPUSER` e `PGAPPASSWORD` (segredo aleatório com pelo menos 32 caracteres) em `.env.docker`; rode `npm run postgres:runtime:provision` após as migrações para criar/atualizar um papel `LOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT` e conceder privilégios às tabelas/sequências existentes, sem acesso à tabela de migrações e sem edição de auditoria. `npm run postgres:runtime:check` confirma a conexão com esse papel. No ambiente Docker local, `mediador_runtime` foi provisionado e validado; a migração 008 foi aplicada e o teste HTTP de inicialização PostgreSQL respondeu com sucesso. Repita o provisionamento depois de cada migração nova. Migrações e bootstrap PostgreSQL continuam usando o papel administrativo, nunca o pool runtime.

No modo `APP_POSTGRES_CONTEXT=1`, a área Envios da tela Minha conta prepara prévias, disponibiliza anexos conferidos por hash, permite aprovação, cancelamento e repreparação, e processa manualmente a fila já aprovada. As rotas usam o contexto do escritório, registram auditoria e não expõem caminhos internos dos anexos. A preparação usa relatórios que atendem os mesmos requisitos da publicação PostgreSQL, incluindo extração concluída, documentos confirmados e CCT válida; itens que não atendem esses requisitos ficam bloqueados com o motivo.

Para criar o primeiro administrador no PostgreSQL, use o comando explícito `npm run postgres:auth:bootstrap -- --nome "Diogo" --email "diogo@example.com"`. Em terminal interativo, ele solicita a senha duas vezes sem exibi-la. Para execução não interativa, forneça `AUTH_BOOTSTRAP_PASSWORD` como variável de ambiente e remova-a ao terminar. O comando usa a conexão administrativa `PGUSER`, insere usuário, credencial e papel global numa transação e recusa segunda inicialização; não use `npm run auth:bootstrap`, que cria o administrador SQLite legado.

### Backup e ensaio de restauração

`npm run postgres:backup` grava um dump PostgreSQL em formato customizado em `data/backups/` (ou em `POSTGRES_BACKUP_PATH`). O arquivo não inclui papéis do PostgreSQL nem os arquivos `.env`/`.env.docker`; preserve a configuração e `CREDENTIALS_MASTER_KEY` em um cofre ou destino seguro separado, pois ela é necessária para ler senhas SMTP cifradas. Para conferir um dump, execute `npm run postgres:backup:validar -- --backup <arquivo.dump>`. O comando cria um banco temporário aleatório no container, restaura o dump, verifica a tabela de migrações e remove esse banco ao final. Ele não altera o banco `mediador`.

No ambiente local, um dump foi criado e a restauração em banco temporário foi validada em 9 de outubro de 2026. O diretório `data/` é ignorado pelo Git; copie o dump para armazenamento externo cifrado conforme a política operacional antes de depender dele como backup de recuperação.

## Estado da migração

O serviço PostgreSQL, o driver `pg`, o migrador versionado e as migrações iniciais estão prontos. `npm run db:migrate` aplica migrações em transações, serializa instâncias concorrentes com advisory lock e detecta alterações em arquivos já aplicados por checksum. O esquema inclui escritório, organizações, vínculos, credenciais/sessões, limites de autenticação e auditoria de segurança; registros monitorados, sindicatos, vínculos sindicato-cliente, configurações de monitoramento e execuções; interpretações privadas versionadas, publicações, trilha de acesso, notificações, configurações SMTP cifradas, decisões de aplicabilidade, fila de envios com tentativas e configurações globais JSONB da plataforma. Constraints compostas impedem relações cliente-contato e publicação-cliente entre escritórios; triggers protegem a propriedade de monitoramentos, interpretações, publicações e envios, e os históricos de auditoria e tentativa são imutáveis. Um índice parcial limita cada cliente a um sindicato principal. A configuração do `.env.docker` é carregada pelo módulo PostgreSQL como fonte complementar às variáveis exportadas e ao `.env`.

A aplicação ainda abre o SQLite por padrão; nenhuma tabela ou dado de produção foi copiado. Os módulos PostgreSQL cobrem leitura/mutações de escritórios, usuários e vínculos; CRUD tenant-scoped de clientes/contatos; catálogo de sindicatos e monitoramentos privados por escritório; revisão de aplicabilidade com versão e invalidação de decisão obsoleta; abertura interna do original por caminho permitido com SHA-256; catálogo documental e vínculo manual aditivo→CCT com revisão concorrente; login, sessões, recuperação; papéis; contextos e concessões de suporte. Confirmação manual exige original íntegro e a abertura é auditada com ator, escritório, cliente e IP. A interpretação PostgreSQL consolida extrações existentes, grava versões imutáveis, permite revisar campos com controle de concorrência e exporta Markdown após validar o estado das decisões. A publicação PDF está disponível em `/api/contexto/publicacoes`: lista sem expor bytes, publica só para cliente/documentos do escritório, revalida o fingerprint depois da geração, salva PDF/hash e auditorias na transação e enfileira notificações; `POST /api/contexto/publicacoes/:id/revogar` revoga a publicação e cancela avisos pendentes. O portal `/api/portal/documentos` só lista publicações ativas do contexto cliente; `/api/portal/documentos/:id` serve PDF após revalidar vínculo e SHA-256, registra abertura/download e grava tentativas negadas sem revelar documentos de outros clientes. `POST /api/portal/documentos/:id/ciencia` registra ciência explícita. A configuração SMTP pode ser lida/atualizada pelo administrador em `/api/contexto/smtp`; senha AES-256-GCM exige `CREDENTIALS_MASTER_KEY` (Base64 de 32 bytes) e nunca retorna pela API. O worker `processarFilaPostgres` processa snapshots de envio previamente aprovados, revalida contexto, destinatário e aplicabilidade e verifica caminhos/hashes de anexos. Notificações de publicação enviam somente link autenticado e têm fila concorrente, cancelamento por vínculo/publicação inválidos e recuperação como `incerto`; migração 007 aplicada no Docker local. Ainda faltam preparação/aprovação de envios a contatos, validação da versão corrente desses relatórios, gatilhos operacionais, integração ao servidor principal e validação de ponta a ponta no banco. Os workers não rodam automaticamente. Handlers HTTP PostgreSQL de autenticação, gestão, decisões, publicações, portal e relatórios aplicam validação de host, origem, sessão, permissões e CSRF. O servidor principal continua usando SQLite; monitoramento agendado, integração coordenada, RLS e importação verificável permanecem pendentes. Não altere a configuração do servidor principal para PostgreSQL até essas etapas estarem concluídas.

Para parar o container mantendo os dados:

```powershell
npm run db:down
```
